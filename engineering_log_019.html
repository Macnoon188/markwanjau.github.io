Engineering Log #019

The Acceptance Test Framework

Engineering by proof.

Date
1 July 2026
Objective
Establish a formal Acceptance Test Framework that verifies architectural behavior rather than isolated software functionality, ensuring every capability introduced into Jaspa OS demonstrates compliance with the architectural principles established throughout the platform.

The Engineering Problem

As the platform matured, a subtle but increasingly important question emerged.

How would we know when Jaspa was actually working?

At first glance, the answer appeared obvious. Run the software. If it produces the expected response, the system works.

That approach is sufficient for many software projects. It is insufficient for an operating system.

Jaspa was no longer a collection of individual components. The Planner depended upon the Capability Registry. The Registry depended upon certified capabilities. Knowledge Providers depended upon the Canonical Data Model. The Reflection Layer depended upon normalized KnowledgeObjects. The Personality Layer depended upon trusted conclusions.

Every architectural layer relied upon the integrity of every preceding layer. Testing each component independently could never prove that the cognitive platform itself functioned correctly.

A Planner could pass every unit test while orchestrating providers incorrectly. A Knowledge Provider could return accurate information while violating the Canonical Data Model. A Reflection Layer could merge evidence successfully while silently discarding trust metadata.

Individually, every subsystem might appear healthy. Collectively, the architecture could still be wrong.

Engineering Commentary

One of the easiest mistakes we could have made would have been measuring progress through implementation metrics — number of providers, lines of code, completed features, passing unit tests.

None of those answered the architectural question we actually cared about:

Can the Cognitive Operating System consistently perform the behaviors its architecture promises?

Rather than asking whether a provider returned the correct answer, we began asking: Did the Planner select the correct capability? Was provider discovery performed through the Registry rather than hardcoded references? Were KnowledgeObjects emitted using the Canonical Data Model? Did trust metadata survive the Reflection Layer? Could every conclusion be traced back to its evidence?

Interestingly, almost none of these questions concerned implementation details. They concerned architectural contracts.

Engineering Principles

Engineering Principle 015
Test architectural behavior, not implementation details.

Implementations evolve. Architectural contracts endure. A mature platform verifies that every subsystem continues honoring the contracts that define the architecture, regardless of how those subsystems are internally implemented.

Engineering Principle 016
Evidence should validate architecture just as architecture validates evidence.

The Trust Framework established that conclusions require evidence. The Acceptance Test Framework extends that philosophy — architectural claims should likewise be supported by demonstrable evidence.

Architecture Decision Record

ADR-014Accepted

Title

Adopt Architecture-Centric Acceptance Testing

Context

Traditional software testing focuses primarily on functional correctness. Jaspa's architecture introduced multiple independently evolving subsystems whose interactions were significantly more important than their isolated implementations. Unit testing alone could not validate these architectural interactions.

Decision

Acceptance Tests shall evaluate complete cognitive workflows rather than isolated software components. Each Acceptance Test shall verify:

  • Planner orchestration
  • Capability discovery
  • Provider interoperability
  • Canonical Data Model compliance
  • Trust preservation
  • Reflection behavior
  • Evidence traceability

Successful completion shall certify architectural behavior rather than merely successful execution.

Consequences

Future providers will not be considered complete simply because they function. They must demonstrate compliance with the cognitive architecture through standardized Acceptance Tests before becoming certified participants within the platform.

Engineering Artifacts

Architectural Verification Pipeline

User Objective ↓ Cognitive Planner ↓ Capability Discovery ↓ Certified Provider(s) ↓ Canonical KnowledgeObjects ↓ Reflection Layer Fusion ↓ Trust Verification ↓ Evidence Traceability ↓ Acceptance Test Outcome

Its purpose is not to inspect implementation. Its purpose is to observe architectural behavior across the complete execution pipeline.

Acceptance Test Scope

Unit Tests ↓ Individual Components Correct Integration Tests ↓ Components Communicate Correctly Acceptance Tests (Jaspa) ↓ Entire Cognitive Architecture Behaves According To Engineering Principles

The architecture should continue behaving consistently regardless of how many capabilities were eventually added.

Lessons Learned

  • Architectural complexity cannot be managed solely through implementation quality.
  • Testing should mirror the abstraction level of the system being evaluated — a cognitive operating system should primarily test cognitive workflows, not isolated methods.
  • Engineering confidence should accumulate gradually; each successful Acceptance Test strengthens confidence in the architectural decisions that made the feature possible.
  • Architectural verification becomes increasingly valuable as ecosystems expand.

// The Next Question

Acceptance Tests had given us confidence that the architecture behaved correctly under controlled conditions. They answered an important question: does the platform work?

Operational engineering introduced a different question:

Why did the platform behave this way?

The user sees only the final answer. The engineer needs visibility into the entire journey — which provider contributed the strongest evidence, why confidence decreased, which stage introduced latency, whether the Planner could have selected a better capability.

Without answers to these questions, every future optimisation would rely on intuition instead of evidence. The next engineering challenge would focus on designing an observability framework capable of making cognitive behaviour explainable.
