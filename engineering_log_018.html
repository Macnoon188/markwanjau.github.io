Engineering Log #018

The Provider SDK

Standardizing extension across the cognitive platform.

Date
1 July 2026
Objective
Design a standardized Provider Software Development Kit (SDK) that enables independent engineers to build Knowledge Providers for Jaspa OS without requiring knowledge of the Cognitive Core, while preserving architectural consistency, compatibility, and long-term maintainability.

The Engineering Problem

The previous engineering log established that Jaspa should remain closed for modification while remaining open for extension. The Extensibility Framework solved one important architectural problem — new capabilities no longer required changes to the Cognitive Core.

For a moment, that seemed sufficient. Then another question emerged.

Suppose two engineers, working on opposite sides of the world, decide to build providers for Jaspa. One creates a Medical Knowledge Provider. The other develops a Scientific Literature Provider. Neither has access to the original design discussions. Neither participated in the architectural decisions recorded throughout this journal.

How should they know what "correct" looks like?

More importantly, how should Jaspa determine whether either provider deserves to become part of the cognitive platform?

Capability should never be granted because code exists. Capability should be earned through compliance with architecture.

That realization shifted the engineering discussion away from extensibility itself and toward something equally important: standardization.

Engineering Commentary

One lesson had quietly repeated itself throughout every previous milestone. Whenever two components interacted successfully, it was because both respected a shared contract.

The Planner trusted the Capability Registry because capability contracts were well defined. The Reflection Layer trusted Knowledge Providers because every provider emitted Canonical KnowledgeObjects. The Trust Framework functioned because every provider attached evidence using the same metadata model.

Success had never depended on implementation. It had depended on agreement.

Ironically, we had already been designing an SDK for several months. We simply had not called it one. Every interface. Every manifest. Every provider lifecycle. Every validation rule. Every Acceptance Test. Each represented a small piece of an unwritten development kit.

Without an SDK, every new provider would become an interpretation of the architecture. With an SDK, every provider becomes an implementation of the architecture. Those are profoundly different outcomes — the first produces architectural drift, the second produces architectural stability.

Engineering Principles

Engineering Principle 013
Every extension should feel native.

A provider that requires special handling is not extending the architecture. It is bypassing it. Every capability admitted into Jaspa should behave as though it had always been part of the operating system. Uniformity is a feature of mature platforms — not a limitation.

Engineering Principle 014
Architecture should define behavior before implementation defines features.

The SDK should not teach engineers how to write code. It should teach them how to participate in the architecture. Implementation details evolve. Architectural contracts should not.

Architecture Decision Record

ADR-013Accepted

Title

Standardize Provider Development Through a Common SDK

Context

Independent provider development had become an architectural requirement following completion of the Extensibility Framework. Allowing providers to evolve without shared engineering standards would eventually introduce incompatible interfaces, inconsistent metadata, fragmented validation strategies, and unpredictable execution behavior. The platform required a common development contract.

Decision

Every provider admitted into Jaspa OS shall be developed using the Provider SDK. The SDK shall define:

  • Provider interfaces
  • Manifest schema
  • Lifecycle hooks
  • Validation rules
  • Registration requirements
  • Testing methodology
  • Compatibility requirements
  • Documentation standards

Certification shall evaluate compliance with these contracts rather than implementation style.

Consequences

The Cognitive Core no longer evaluates provider implementations directly. Instead, it evaluates architectural compliance. This shifts responsibility away from individual engineering judgement and toward repeatable engineering standards.

Engineering Artifacts

The Provider Development Lifecycle

Engineer ↓ Implements Provider ↓ Implements SDK Interfaces ↓ Provider Manifest ↓ Manifest Validation ↓ Capability Verification ↓ Certification Pipeline ↓ Capability Registry ↓ Planner Discovery ↓ Execution DAG ↓ Reflection Layer ↓ Cognitive Response

One observation immediately stands out. The Cognitive Core never appears during provider development. Everything before registration occurs outside the runtime.

That separation was intentional. The architecture should reject invalid providers before execution ever begins.

SDK Responsibility Boundary

Provider SDK Interfaces · Manifest Schema · Validation Rules Lifecycle Hooks · Test Templates Certification Rules · Documentation Standards ↓ Every Provider Looks Identical To The Cognitive Core

The SDK does not eliminate creativity. It standardizes the architectural surface presented to the operating system.

Just as device drivers abstract hardware differences behind consistent interfaces, the Provider SDK abstracts domain-specific knowledge behind a uniform architectural contract. The operating system does not need to understand the internal design of a provider. It only needs confidence that the provider satisfies the contracts required to participate safely within the cognitive platform.

Lessons Learned

  • Ease of development can accelerate an ecosystem, but only architectural discipline can sustain one.
  • Standards should be discovered from existing agreements, not invented from scratch.
  • Certification should evaluate compliance with contracts, not implementation style.
  • Rejecting invalid providers before runtime protects the stability of the whole platform.

// The Next Question

The SDK made correctness the default outcome of provider development. But defining what "correct" means is not the same as proving that a given provider — or the platform as a whole — actually achieves it.

How would we know when Jaspa was actually working?

Run the software. If it produces the expected response, does the system work? That approach is sufficient for many software projects. It is insufficient for an operating system whose layers depend on one another's integrity.

That question would lead directly to the design of the Acceptance Test Framework — a way to verify architectural behavior, not just isolated software functionality.
