Engineering Log #002

The Problem with Traditional AI Assistants

Date
June 2026
Objective
Determine why existing AI assistants — even the most capable large language models — were insufficient for long-term engineering work, and establish the architectural principles that would eventually distinguish Jaspa OS from a conventional chatbot.

Problem — The Question That Changed Everything

After months of using AI for software development, cybersecurity, infrastructure planning, and documentation, one question kept resurfacing.

Not because the models lacked intelligence.

Because they lacked continuity.

Every new conversation required rebuilding context. Projects had to be explained again. Architectural decisions had to be repeated. The assistant answered well, but it did not participate in engineering.

That distinction became impossible to ignore.

At first, this seemed like a limitation of the underlying language model. In reality, it was a limitation of the surrounding architecture.

The more I thought about it, the more obvious it became:

The problem wasn't the AI. The problem was how we were asking it to work.

Observations from Real Projects

This realization didn't happen in isolation. It emerged from dozens of ongoing projects that shared the same underlying frustration. Some of them included:

  • Building a Proxmox-based homelab for cybersecurity experimentation.
  • Deploying Wazuh and integrating it with pfSense.
  • Developing a React Native church application.
  • Building Hermes as an AI assistant running inside a dedicated Ubuntu Server virtual machine.
  • Designing my engineering portfolio and documenting technical projects.
  • Creating automation workflows that could be triggered remotely through Telegram.

Each project revealed the same pattern.

The AI could solve today's problem. Tomorrow, it would need the same explanation all over again.

That wasn't a failure of intelligence. It was a failure of engineering continuity.

The Engineering Conversation

One of the earliest architectural discussions captured this perfectly.

Conversation Extract
Mark

"Let's move to phase 2 of improving Jaspa. Here, I want him to have knowledge of all historical facts, a very vast knowledge of the Bible (and have the ability to relate it to current times based on sermons that it can search from the internet), and lastly... I don't know how you did it, but you explain things almost like you have a personality. How can we do the same for Jaspa?"

That single message contained far more than a feature request.

Without realizing it, it defined the roadmap for the entire platform. Hidden inside it were four completely different engineering problems.

Problem One

Knowledge

How should biblical information be stored?

Problem Two

Reasoning

How should ancient scripture be connected with modern events?

Problem Three

Personality

How should responses feel consistent without becoming scripted?

Problem Four

Growth

How could new capabilities be added years later without rewriting the platform?

Engineering Commentary

Most AI projects begin by adding features. This project deliberately moved in the opposite direction.

Rather than immediately implementing Bible knowledge or personality, we paused and asked a more fundamental question:

"If Jaspa eventually knows hundreds of different domains, how should those domains be organized?"

That single question transformed the project. Instead of designing features, we began designing an operating system.

Hypothesis — The First Architectural Shift

Originally, the mental model looked like this.

User ↓ Large Language Model ↓ Response

It was simple. It worked. It was also a dead end.

Every responsibility lived inside one component. The model had to: reason, search, remember, retrieve, summarize, verify, and respond — all at the same time.

As capabilities increased, complexity would increase with them.

A Better Question

Instead of asking

"Can the AI answer this?"

we started asking

"Who should answer this?"

That subtle change completely altered the architecture. Instead of one intelligent component doing everything, Jaspa would become a coordinator capable of selecting the most appropriate source of intelligence.

This idea eventually evolved into the Capability-Based Planner, one of the defining characteristics of Jaspa OS.

Implementation — The Birth of an Engineering Philosophy

Around this point, an engineering philosophy quietly emerged. It wasn't written down immediately. It revealed itself through repeated conversations.

Those conversations eventually crystallized into five guiding beliefs.

01

Intelligence Is a System

No single model should carry every responsibility. Specialized components should collaborate.

02

Architecture Outlives Models

Language models improve every year. Architectures should survive for decades.

03

Every Capability Should Be Replaceable

Today's search provider may not exist tomorrow. Today's reasoning model may eventually be obsolete. Replacing either should never require rewriting the planner.

04

Every Decision Should Be Observable

Engineering without visibility becomes guesswork. The platform should eventually explain not only what it answered, but how it arrived there.

05

Growth Should Be Predictable

Adding Bible knowledge should follow the same architectural pattern as adding historical knowledge, cybersecurity expertise, or technical documentation. No special cases. No exceptions.

Result — Looking Ahead

By the end of this discussion, something remarkable had happened.

We had not written a single line of production logic. No provider existed. No planner had been implemented. No registry had been designed.

And yet, the architecture had already begun taking shape.

Engineering Observation

This would prove to be one of the most important lessons of the entire project.

Good engineering begins long before the first implementation.

Lessons Learned

  • The quality of an AI system is determined as much by its architecture as by the model it uses.
  • Real engineering requires continuity, not isolated conversations.
  • Asking "Who should solve this problem?" produces better architectures than asking "Can the model solve it?"
  • Feature requests often reveal deeper architectural requirements.
  • A clear philosophy established early prevents countless redesigns later.
