Engineering Log #007

The Provider Registry

Teaching the platform how to discover its own intelligence.

Date
28 June 2026
Objective
Eliminate hardcoded knowledge dependencies by introducing a dynamic Provider Registry capable of discovering, validating, and exposing platform capabilities at runtime. This milestone marks the transition from orchestration design to a truly extensible cognitive architecture.

The Engineering Problem

Engineering Log #006 ended with an uncomfortable realization.

The Cognitive Router had learned how to think. It could understand requests, determine intent, estimate complexity, and build execution plans.

But it had one major limitation.

It didn't know where capabilities lived.

Imagine a request requiring Scriptural Exegesis. Where should the Router send it? A Bible provider? A theology provider? A cloud API? A local database?

Every answer required hardcoding.

And hardcoding meant the architecture had already failed.

Engineering Commentary

One sentence became our guiding principle during this phase:

The planner should never know provider names.

That statement seems small. Architecturally, it changes everything.

If the Router begins saying use_bible_provider(), the platform becomes permanently dependent on that provider. Replace the provider. The Router breaks.

Instead, the Router should only know this:

Capability Required — Scriptural Exegesis

Everything else should happen automatically.

Engineering Artifact 007-A

Original Jaspa Response

After reviewing the revised architecture, Jaspa proposed a different direction.

Response • Jaspa OS
Jaspa

"I have implemented the hybrid provider architecture and the core logic for the dynamic Provider Registry."

Provider Structure

Defined in PROVIDER_INTERFACE.md. Every provider must contain:

  • manifest.yaml
  • implementation.py
  • tests/

Registry Core

Created registry.py. Dynamically discovers providers, validates manifests, and indexes capabilities.

Extensible Design

The Router now performs lookups against the Registry's capability map, making it completely agnostic to provider names.

Engineering Analysis

This response marked one of the largest architectural advances in the project.

Notice what changed. The Router no longer searched for providers. It searched for capabilities.

That distinction introduced complete decoupling.

Before the Registry

Router ↓ Bible Provider ↓ Internet Provider ↓ Memory Provider

Every connection was permanent. Adding one provider meant editing the Router.

After the Registry

Cognitive Router ↓ Capability Registry ↓ ┌──────────────────┼──────────────────┐ ↓ ↓ ↓ Bible Provider Internet Provider Memory Provider ↓ ↓ ↓ Capabilities Capabilities Capabilities

The Router no longer cared which provider existed. It simply requested a capability. The Registry handled the rest.

The Manifest Philosophy

The Registry introduced another elegant idea.

Providers should describe themselves.

Instead of writing code like register_bible_provider(), providers would advertise their own capabilities.

Example:

provider: bible capabilities: - scripture_lookup - biblical_context - biblical_person_lookup - cross_reference - original_language_lookup

The Registry simply asked:

"Who can perform Scripture Lookup?"

Every matching provider could respond. No Router modification required.

Engineering Principle 003
Providers register themselves. The platform discovers capabilities. The planner never discovers providers.

The Hidden Advantage

Initially, the Registry appeared to solve only one problem — removing hardcoded provider names.

Months later, we realized it solved several more.

  • Hot-swappable providers.
  • Multiple providers offering identical capabilities.
  • Easier testing.
  • Versioned providers.
  • Future cloud integration.
  • Dynamic loading.
  • Runtime diagnostics.

One architectural decision unlocked years of future flexibility.

Engineering Artifact 007-B

Validation Results

After implementing the Registry, Jaspa reported:

Response • Jaspa OS
Jaspa

"The Provider Registry has been successfully validated."

Validation Summary

  • ✔ Discovery successful.
  • ✔ Capability indexing successful.
  • ✔ Invalid manifests handled safely.
  • ✔ Startup health reporting implemented.

Engineering Analysis

Notice what was tested. Not Bible knowledge. Not search. Not reasoning.

Instead, the engineering effort focused entirely on ensuring the platform could reliably discover and validate providers before they participated in execution.

This is classic platform engineering. Infrastructure first. Features second.

Engineering Reflection

The Registry became something of a librarian.

It never answered questions. It never interpreted Scripture. It never searched the internet.

It simply knew where every capability lived.

Engineering Observation

Ironically, one of the least intelligent components became one of the most valuable.

Lessons Learned

  • Capabilities are more stable than implementations.
  • Self-describing providers dramatically reduce coupling.
  • Discovery scales better than configuration.
  • Validation belongs at startup, not during execution.
  • Platform engineering often means building systems that users never notice.

// The Next Question

The Provider Registry solved a major architectural challenge. The Router could now discover who could perform the required work.

But another question immediately surfaced.

What if a single request required multiple capabilities?

Consider the query: "Explain how David's kingship foreshadows Christ, relate it to modern Christian leadership, and reference current sermons discussing this theme."

No single provider could satisfy that request. The platform would need to coordinate multiple providers, determine execution order, respect dependencies, and merge the results into one coherent answer.

This raised the next engineering challenge:

How do you coordinate many independent providers without creating chaos?

The answer would become the Execution Engine and, ultimately, the execution graph (DAG) that allowed Jaspa OS to think in parallel while remaining deterministic.
